# 工作空间 Workflow

## 1. 创建任务

每项开发工作开始前，应先明确：

* 任务背景。
* 当前问题。
* 期望结果。
* 验收标准。
* 业务影响。
* 数据影响。
* 安全和隐私影响。
* 部署影响。
* 明确不在本次范围内的内容。

任务应尽量对应一个可独立验证的业务闭环，不把多个无关目标混入同一任务。

## 2. 创建开发分支

开始修改前：

1. 确认当前工作区状态。
2. 确认没有未知的未提交修改。
3. 获取最新 `main`。
4. 从最新 `main` 创建开发分支。
5. 不直接在 `main` 开发。

分支命名使用：

* `feat/<name>`
* `fix/<name>`
* `refactor/<name>`
* `test/<name>`
* `docs/<name>`
* `chore/<name>`

不得使用破坏性 Git 命令清理未经确认的工作区内容。

## 3. 阅读任务相关上下文

修改前至少检查：

* `README.md`
* `package.json`
* `tsconfig.json`
* `vite.config.ts`
* `wrangler.jsonc`
* `.github/workflows/`
* `db/schema.ts`
* 相关 `docs/phase-*.md`
* 相关页面、API、业务服务和测试

确认：

* 当前技术栈。
* 当前运行方式。
* 当前数据库结构。
* 当前权限实现。
* 当前 CI 和部署流程。
* 当前业务阶段和状态规则。
* 当前导出与归档结构。

文档与代码冲突时，以实际代码和运行结果为依据，并将文档修正纳入任务。

## 4. 建立修改前基线

### 缺陷任务

先完成：

1. 复现问题。
2. 记录触发步骤。
3. 记录实际结果。
4. 明确期望结果。
5. 定位问题发生层级。
6. 确认是否已有相关测试。
7. 区分原有错误和本次修改产生的错误。

### 功能任务

先完成：

1. 确认当前功能边界。
2. 查找已有相似实现。
3. 确认可复用的组件、服务和数据模型。
4. 明确缺失部分。
5. 判断是否影响已有工作台。
6. 判断是否需要接入 Archive、Export 或 Control Tower。

本地开发使用：

`npm ci`

`npm run dev`

不得在未理解当前行为前直接进行大范围修改。

## 5. 执行影响分析

### 页面和 UI 修改

检查：

* `app/` 下相关页面。
* Server Component 与 Client Component 边界。
* 现有组件和样式。
* 桌面端和移动端。
* 加载、空、错误和禁用状态。
* 键盘操作和可访问性。
* 是否涉及打印布局。
* 是否涉及公开页面缓存。

### API 修改

检查：

* 对应 `route.ts`。
* 请求方法。
* 身份认证。
* 管理员权限。
* 跨域写入防护。
* 输入校验。
* 状态机校验。
* 幂等和重复提交。
* 并发冲突。
* 错误响应。
* 调用方兼容性。

### 数据库修改

检查：

* `db/schema.ts`。
* 现有表关系。
* 外键。
* 索引。
* 唯一约束。
* 默认值。
* nullability。
* 级联删除。
* 旧数据兼容。
* Migration。
* Archive 和导出影响。

### R2 媒体修改

检查：

* 对象键生成。
* MIME 类型和大小限制。
* 公开或私密访问。
* 缓存策略。
* 上传失败处理。
* 数据库失败后的对象清理。
* 替换与删除行为。
* Media Manifest。
* 图片替代文本。

### 认证和权限修改

检查：

* `getChatGPTUser()`。
* `requireApiAdmin()`。
* `rejectCrossOriginWrite()`。
* `isAdminEmail()`。
* 登录身份是否只在服务端读取。
* 公共和管理员接口是否严格分离。
* 是否泄露管理员信息或用户身份。

### 部署修改

检查：

* `package.json`
* `vite.config.ts`
* `wrangler.jsonc`
* `worker/`
* `.github/workflows/`
* D1 binding
* R2 binding
* GitHub Secrets
* 环境变量
* Migration 执行方式

## 6. 设计垂直业务切片

涉及完整功能时，按以下顺序设计：

1. 数据结构。
2. Migration。
3. 数据访问。
4. 业务规则。
5. 状态机。
6. 权限。
7. API。
8. 页面和交互。
9. 媒体处理。
10. Archive。
11. JSON、CSV 或 iCal 导出。
12. Season Control Tower 聚合。
13. 测试。
14. 文档。

不得只完成 UI，再临时拼接缺乏约束的数据层。

每个切片应能独立回答：

* 数据保存在哪里。
* 谁可以读取。
* 谁可以修改。
* 当前状态允许哪些操作。
* 失败后如何恢复。
* 历史记录如何保留。
* 是否进入归档和导出。

## 7. 数据库实施流程

涉及 Schema 变化时：

1. 修改 `db/schema.ts`。
2. 明确字段类型和含义。
3. 明确是否允许为空。
4. 明确默认值。
5. 明确索引和唯一约束。
6. 明确外键和删除行为。
7. 评估旧数据兼容性。
8. 执行：

`npm run db:generate`

9. 人工检查生成 SQL。
10. 确认没有意外删除或重建。
11. 检查新数据库创建。
12. 检查已有数据库升级。
13. 更新数据访问逻辑。
14. 更新 Archive。
15. 更新导出。
16. 更新相关阶段文档。

已经进入共享或生产环境的旧 migration 不得回写修改。

需要修正时必须新增 migration。

## 8. 业务规则与状态机实施

每个状态变更必须：

1. 读取当前状态。
2. 检查当前状态是否允许目标操作。
3. 检查所有前置事实。
4. 检查关键阻塞项。
5. 检查当前用户权限。
6. 执行原子状态更新。
7. 保存必要审计信息。
8. 返回明确结果。

不得允许客户端直接提交任意状态值。

以下人工决定不得自动执行：

* 发布。
* 设计评审。
* 材料批准。
* 技术包批准和锁定。
* 试身批准。
* 封样。
* `NERA-SEAL`。
* 生产放行。
* `NERA-GO`。
* 生产偏差决定。
* 联系人确认。
* 外联批准和发送登记。

不可变记录需要变更时，应创建新一轮、新修订或新时间线记录。

## 9. API 实施流程

实现或修改 API 时：

1. 明确请求方法和路由。
2. 定义输入结构。
3. 进行运行时校验。
4. 标准化字符串、日期、数组和枚举。
5. 对 Studio 写接口执行跨域来源检查。
6. 验证登录身份。
7. 验证管理员权限。
8. 检查目标资源是否存在。
9. 检查当前业务状态。
10. 检查重复提交和并发冲突。
11. 执行业务写入。
12. 处理事务或补偿清理。
13. 返回最小必要数据。
14. 使用明确 HTTP 状态码。
15. 不暴露内部异常细节。
16. 添加正常与异常路径测试。

异常路径至少覆盖：

* 非法输入。
* 缺失字段。
* 未登录。
* 无权限。
* 非法来源。
* 资源不存在。
* 状态冲突。
* 重复提交。
* 并发冲突。
* 数据库失败。
* R2 失败。
* 文件过大。

## 10. R2 媒体实施流程

上传媒体时：

1. 校验文件是否存在。
2. 校验文件大小。
3. 校验 MIME 类型。
4. 校验允许的媒体类别。
5. 生成稳定且不可预测的对象键。
6. 上传到正确的公共或私密区域。
7. 写入数据库引用。
8. 数据库失败时清理未引用对象。
9. 保存媒体类型、大小和替代文本。
10. 更新 Media Manifest。

替换媒体时：

1. 保留业务记录和稳定链接。
2. 上传新对象。
3. 更新数据库引用。
4. 确认新对象可用。
5. 再处理旧对象。
6. 删除旧对象前检查其他引用。

删除媒体时：

1. 检查是否仍被作品、系列或业务记录引用。
2. 检查是否属于不可变证据。
3. 检查是否已经进入归档。
4. 获得必要权限。
5. 删除数据库关系。
6. 删除无引用 R2 对象。
7. 记录必要审计信息。

## 11. UI 实施流程

页面实现应遵循：

1. 优先复用现有组件和视觉语言。
2. 默认使用 Server Component。
3. 只有必要交互使用 Client Component。
4. 不把权限逻辑放到客户端。
5. 实现正常状态。
6. 实现加载状态。
7. 实现空状态。
8. 实现错误状态。
9. 实现禁用状态。
10. 提供明确操作反馈。
11. 检查长文本。
12. 检查缺失图片。
13. 检查异常数据。
14. 检查桌面端。
15. 检查移动端。
16. 检查键盘操作。
17. 检查可访问性。
18. 检查打印页面，如适用。

涉及危险操作时：

* 使用明确文案。
* 展示实际影响。
* 提供二次确认。
* 不使用含糊按钮名称。

## 12. Archive 与导出实施流程

新增业务数据时，必须评估：

* 是否应进入 Archive 快照。
* 是否需要更新 Archive 版本。
* 是否应进入媒体清单。
* 是否应进入 JSON 导出。
* 是否应进入 CSV 导出。
* 是否应进入 iCal 导出。
* 是否包含敏感字段。
* 是否需要稳定关联 ID。
* 是否需要变更对比支持。

Archive 快照必须：

* 保持不可变。
* 保留稳定结构。
* 包含必要关系。
* 包含媒体对象清单。
* 保持摘要校验。
* 不包含明文展厅 Token。
* 不静默遗漏新增业务模块。

CSV 导出必须防止公式注入。

## 13. Season Control Tower 接入流程

新增或修改关键业务阶段时，检查是否需要接入 Control Tower。

接入时：

1. 只读取明确事实。
2. 定义通过条件。
3. 定义阻塞条件。
4. 定义逾期判断。
5. 提供可解释原因。
6. 深链回原始工作台。
7. 不自动改变状态。
8. 不返回敏感信息。
9. 不使用隐藏权重。
10. 不重复计算已有指标。

Control Tower 只能用于汇总、提醒和导航。

## 14. 渐进式验证

开发过程中按修改范围执行：

`npm run lint`

`npx tsc --noEmit`

数据库变化执行：

`npm run db:generate`

并人工检查 migration。

同时执行相关：

* 单元测试。
* API 测试。
* 页面检查。
* 状态机测试。
* 权限测试。
* R2 上传和清理测试。
* 导出测试。

小步开发时不必每次执行完整构建，但相关局部检查必须持续通过。

## 15. 完整验证

Pull Request 前按照 CI 等价流程执行：

`npm ci`

`npm run lint`

`npx tsc --noEmit`

`npx vinext build`

`npm run validate:artifact`

`node --test tests/rendered-html.test.mjs`

也可以执行项目封装命令：

`npm run build`

`npm test`

数据库变化还必须验证：

* Migration 生成结果。
* 新数据库初始化。
* 已有数据库升级。
* 外键和唯一约束。
* Archive。
* JSON 和 CSV 导出。

UI 变化还必须人工检查：

* 桌面端。
* 移动端。
* 键盘操作。
* 加载状态。
* 空状态。
* 错误状态。
* 打印布局。

## 16. 安全与隐私自审

提交前确认：

* 所有 Studio 写接口都验证管理员。
* 所有写接口执行来源校验。
* 公共接口只返回公开数据。
* 没有把权限判断放在客户端。
* 没有泄露完整展厅 Token。
* 没有泄露管理员邮箱。
* 没有泄露联系人邮箱或电话。
* 没有泄露私密对象键。
* 没有公开试身或封样证据。
* 没有把内部异常返回客户端。
* 没有提交 `.env`、密钥或 Token。
* 没有自动发送外部信息。
* 没有绕过人工批准。
* 没有修改不可变历史记录。

## 17. 数据完整性自审

确认：

* 多表写入不会产生部分成功。
* R2 和 D1 失败时有明确清理或补偿。
* 重复提交不会创建重复记录。
* 并发操作不会绕过状态机。
* 唯一约束正确。
* 外键和级联行为正确。
* 稳定 ID 和 slug 未被破坏。
* 已批准记录不会被原地覆盖。
* 新业务数据进入正确的 Archive 和导出。
* 删除操作不会误删仍被引用的数据或媒体。

## 18. Diff 自审

提交前检查完整 Diff：

* 是否只包含当前任务。
* 是否存在无关格式化。
* 是否包含调试日志。
* 是否包含临时代码。
* 是否包含注释掉的旧实现。
* 是否包含真实凭证。
* 是否包含构建产物。
* 是否遗漏 migration。
* 是否遗漏测试。
* 是否遗漏文档。
* 是否破坏公共接口。
* 是否改变产品定位。
* 是否破坏视觉一致性。
* 是否重复已有业务逻辑。

## 19. Commit 流程

Commit 前：

1. 检查 `git status`。
2. 检查完整 Diff。
3. 执行必要验证。
4. 只暂存相关文件。
5. 使用 Conventional Commits。
6. 确保 Commit 与实际修改一致。

推荐格式：

* `feat: add material approval workflow`
* `fix: prevent duplicate showroom requests`
* `refactor: centralize publication validation`
* `test: cover private media access`
* `docs: update Cloudflare deployment guide`
* `ci: separate pull request verification from deploy`

每个 Commit 应是一个完整逻辑单元。

## 20. Pull Request 流程

PR 标题使用 Conventional Commits 风格。

PR 描述至少包含：

### Summary

* 本次解决的问题。
* 实现后的最终行为。

### Scope

* 涉及页面。
* 涉及 API。
* 涉及业务阶段。
* 明确没有修改的内容。

### Database

* 是否修改 Schema。
* 是否包含 migration。
* 是否影响已有数据。
* 是否需要生产迁移步骤。

### Media

* 是否修改 R2。
* 是否新增对象类型。
* 是否影响公共或私密缓存。
* 是否更新 Media Manifest。

### Security and Privacy

* 认证和权限影响。
* 私密数据影响。
* Token 和个人信息影响。

### Archive and Export

* 是否更新 Archive。
* 是否更新 JSON、CSV 或 iCal。
* 是否修改 Archive 版本。

### Verification

列出实际执行的命令和结果。

### UI Evidence

涉及 UI 时提供：

* 桌面端截图。
* 移动端截图。
* 必要的打印预览。

### Deployment

* 是否修改 Worker。
* 是否修改 bindings。
* 是否修改环境变量。
* 是否修改 CI。
* 是否需要额外部署步骤。

### Rollback

说明出现问题时如何安全回退。

## 21. Review 与合并

合并前必须确认：

* PR 范围清晰。
* Review 意见已处理。
* CI 全部通过。
* 没有未解决冲突。
* Migration 已检查。
* 权限边界正确。
* 私密媒体仍受保护。
* Archive 和导出已同步。
* 文档已更新。
* 回滚方式明确。

默认使用 squash merge。

不得为了合并：

* 删除失败测试。
* 跳过 CI。
* 降低权限校验。
* 忽略数据风险。
* 强制覆盖 `main`。

## 22. 部署流程

部署由 GitHub Actions 在合并或推送到 `main` 后执行。

Pull Request 阶段只验证，不应部署生产。

部署前确认：

* 目标 Commit 正确。
* CI 全部通过。
* Cloudflare Secrets 已配置。
* D1 binding 正确。
* R2 binding 正确。
* `wrangler.jsonc` 正确。
* Worker 入口正确。
* Migration 已制定执行计划。
* 回滚方式明确。

未经明确授权，不手动：

* 修改生产 D1 数据。
* 删除生产 R2 对象。
* 更改生产管理员邮箱。
* 更改生产访问策略。
* 绕过 GitHub Actions 部署。

## 23. 部署后检查

部署完成后至少检查：

### 公共端

* 首页。
* 公开作品页。
* Collection。
* Digital Lookbook。
* Process Dossier。
* Press Room。
* 公共媒体。

### Studio

* 设计师登录。
* 管理员权限。
* Studio 首页。
* 一项代表性读取操作。
* 一项受控写入操作。
* 未授权访问是否被拒绝。

### 数据与媒体

* D1 读取。
* D1 写入。
* R2 上传。
* R2 读取。
* 公共媒体缓存。
* 私密媒体保护。

### 导出

* JSON。
* CSV。
* iCal。
* Archive 快照。
* Media Manifest。

### 运行状态

* Worker 日志。
* 新增异常。
* 认证错误。
* 数据库错误。
* R2 错误。
* 5xx 响应。

## 24. 生产异常处理

发现生产异常时：

1. 停止继续部署和扩大修改。
2. 保留日志和错误信息。
3. 记录受影响 Commit。
4. 记录触发步骤。
5. 判断影响范围。
6. 判断是否涉及数据损坏。
7. 判断回滚或前向修复。
8. 不执行未经确认的数据清理。
9. 不直接修改数据库掩盖问题。
10. 修复后重新执行完整验证和部署后检查。

涉及数据完整性时，优先保护 D1 和 R2 中的现有事实记录。

## 25. 最终交付

任务完成后必须汇报：

* 实现结果。
* 核心修改。
* 修改原因。
