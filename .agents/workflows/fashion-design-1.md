# 全局 Workflow

## 1. 任务解析

开始工作前，必须先明确：

* 任务目标。
* 验收标准。
* 当前问题。
* 期望结果。
* 修改范围。
* 明确不在本次范围内的内容。
* 是否涉及高风险操作。

任务类型应归类为：

* 功能开发
* 缺陷修复
* 重构
* 测试
* 文档
* 数据库
* 部署
* 安全
* 配置
* 性能优化

以下内容视为高风险操作：

* 身份认证和权限
* 数据库迁移
* 数据删除
* 对象存储删除
* 生产部署
* 外部消息发送
* 密钥和环境变量
* 依赖大版本升级
* 公共接口变更
* 不可逆状态变更

## 2. 检查工作区

修改前检查：

* 当前 Git 分支。
* 工作区是否存在未提交修改。
* 未提交修改是否属于当前任务。
* 是否需要从最新默认分支创建新分支。
* 是否存在合并冲突。
* 是否存在未跟踪文件。
* 是否有其他开发者留下的修改。

不得擅自：

* 清理未知修改。
* 覆盖已有修改。
* 重置工作区。
* 删除未跟踪文件。
* 切换分支导致修改丢失。

## 3. 阅读项目约定

开始开发前阅读：

* README。
* AGENTS.md。
* CONTRIBUTING。
* 项目规则和工作流。
* package 配置。
* 编译配置。
* lint 配置。
* 测试配置。
* CI 配置。
* 部署配置。
* 与任务有关的业务文档。

确认：

* 使用的包管理器。
* 运行时版本。
* 安装命令。
* 开发命令。
* 构建命令。
* lint 命令。
* 类型检查命令。
* 测试命令。
* 数据库迁移命令。
* 部署方式。

## 4. 定位相关代码

根据任务查找：

* 页面入口。
* API 入口。
* 业务服务。
* 数据访问层。
* 数据模型。
* 权限逻辑。
* 公共组件。
* 类型定义。
* 测试文件。
* 配置文件。
* 最近相关提交。

必须理解：

* 当前调用链。
* 数据流。
* 状态变化。
* 错误处理。
* 权限边界。
* 已有测试覆盖。
* 可能受影响的其他模块。

不得仅修改第一个搜索到的文件，而不检查完整调用关系。

## 5. 建立修改前基线

缺陷任务应先：

1. 复现问题。
2. 记录触发条件。
3. 确认实际结果。
4. 确认期望结果。
5. 定位问题层级。
6. 记录修改前已有失败。

功能任务应先：

1. 确认当前行为。
2. 确认已有能力。
3. 判断是否存在可复用实现。
4. 明确缺失部分。
5. 确认新功能不会重复现有功能。

基线检查应使用最小必要命令，避免在尚未修改时进行无意义的全量操作。

## 6. 制定实施方案

实施前应形成清晰方案，包括：

* 修改哪些模块。
* 每个模块的职责。
* 数据如何流动。
* 状态如何变化。
* 输入如何校验。
* 权限如何控制。
* 错误如何处理。
* 是否涉及数据库。
* 是否涉及对象存储。
* 是否涉及接口兼容性。
* 是否需要迁移。
* 是否需要新增测试。
* 是否需要更新文档。
* 如何回滚。

复杂任务应拆分为多个可验证步骤。

不得在没有理解整体影响的情况下直接进行大范围修改。

## 7. 控制任务范围

实施过程中：

* 只修改完成当前任务所必需的内容。
* 不进行无关重构。
* 不升级无关依赖。
* 不批量格式化无关文件。
* 不改变未被要求的公共接口。
* 不改变未被要求的产品行为。
* 不删除仍可能被使用的旧逻辑。

发现额外问题时：

* 判断是否会阻止当前任务完成。
* 不阻止当前任务的，记录为独立问题。
* 会阻止当前任务的，进行最小必要修复。
* 明确说明任务范围是否扩大。

## 8. 分步实施

按照小步修改原则进行：

1. 先修改最底层数据或业务规则。
2. 再修改调用层和接口。
3. 再修改页面和交互。
4. 最后补充测试和文档。

每完成一个逻辑步骤，应进行最小相关检查。

保持每一步：

* 可理解。
* 可验证。
* 可回退。
* 不依赖隐藏状态。
* 不产生大量临时修改。

复杂功能优先完成垂直闭环，而不是同时铺开多个未完成模块。

## 9. 数据库修改流程

涉及数据库时：

1. 阅读现有 Schema。
2. 确认表关系和约束。
3. 设计字段类型。
4. 设计默认值。
5. 设计 nullability。
6. 设计索引。
7. 设计唯一约束。
8. 设计外键和删除行为。
9. 考虑旧数据兼容。
10. 生成 migration。
11. 人工检查 migration。
12. 测试新数据库。
13. 测试已有数据升级。
14. 更新数据访问代码。
15. 更新导出和归档。
16. 更新文档。

不得：

* 直接修改生产数据库代替 migration。
* 回写已经应用的 migration。
* 通过删除表规避迁移设计。
* 忽略旧数据和回滚风险。

## 10. API 修改流程

涉及 API 时：

1. 确认调用方。
2. 明确请求方法。
3. 定义输入结构。
4. 添加运行时校验。
5. 验证身份。
6. 验证权限。
7. 验证请求来源。
8. 检查目标资源。
9. 检查业务状态。
10. 执行业务操作。
11. 处理事务和回滚。
12. 处理重复提交。
13. 返回明确状态码。
14. 返回最小必要数据。
15. 添加正常和异常测试。
16. 检查旧调用方兼容性。

不得把数据库异常或内部错误直接返回客户端。

## 11. UI 修改流程

涉及 UI 时：

1. 阅读现有设计模式。
2. 复用已有组件。
3. 确认 Server 和 Client 边界。
4. 实现正常状态。
5. 实现加载状态。
6. 实现空状态。
7. 实现错误状态。
8. 实现禁用状态。
9. 检查桌面端。
10. 检查移动端。
11. 检查键盘操作。
12. 检查可访问性。
13. 检查长文本和异常数据。
14. 检查打印布局，如适用。

不得只验证理想数据下的视觉效果。

## 12. 渐进式验证

开发过程中优先执行与修改直接相关的检查：

* 单文件或相关目录 lint。
* TypeScript 类型检查。
* 相关单元测试。
* 相关接口测试。
* 相关页面检查。
* migration 生成和检查。

每次小修改后不必重复完整构建，但必须及时发现局部问题。

发现错误时：

1. 判断是否由本次修改引入。
2. 定位根因。
3. 不使用临时绕过掩盖问题。
4. 修复后重新执行相关检查。

## 13. 完整验证

任务完成后，按项目支持情况执行：

1. 依赖安装验证。
2. lint。
3. 类型检查。
4. 单元测试。
5. 接口测试。
6. 集成测试。
7. 完整构建。
8. 构建产物验证。
9. 数据库迁移验证。
10. 人工页面检查。
11. 权限检查。
12. 安全检查。

验证结果必须如实记录：

* 已执行并通过。
* 已执行但失败。
* 未执行。
* 无法执行。
* 因何无法执行。

不得把“未执行”描述为“通过”。

## 14. 安全复核

提交前检查：

* 是否新增敏感数据泄露。
* 是否在客户端执行权限判断。
* 是否缺少身份认证。
* 是否缺少权限校验。
* 是否缺少输入校验。
* 是否存在跨域写入风险。
* 是否存在重复提交风险。
* 是否存在并发冲突。
* 是否存在部分写入。
* 是否在日志中暴露隐私。
* 是否返回完整内部异常。
* 是否可能误删数据或文件。
* 是否缺少审计记录。
* 是否存在不可逆操作。

高风险修改必须说明：

* 风险是什么。
* 如何降低风险。
* 如何验证。
* 如何回滚。

## 15. Diff 自审

提交前检查完整 Diff：

* 是否只包含当前任务修改。
* 是否意外修改无关文件。
* 是否包含调试代码。
* 是否包含临时日志。
* 是否包含注释掉的旧代码。
* 是否包含真实凭证。
* 是否包含构建产物。
* 是否遗漏测试。
* 是否遗漏文档。
* 是否遗漏 migration。
* 是否改变公共接口。
* 是否破坏兼容性。
* 是否存在重复逻辑。
* 命名是否与项目一致。
* 错误处理是否完整。

## 16. Commit 流程

提交前：

1. 确认工作区状态。
2. 检查 Diff。
3. 执行必要验证。
4. 只暂存相关文件。
5. 使用准确的 Commit 类型。
6. 编写清晰 Commit 信息。

Commit 应满足：

* 一个 Commit 对应一个完整逻辑单元。
* 不混入无关修改。
* 不包含本地配置。
* 不包含失败产物。
* 不包含敏感信息。
* Commit 信息与实际修改一致。

## 17. Pull Request 流程

Pull Request 应包括：

### Summary

* 修改了什么。
* 解决了什么问题。
* 最终行为是什么。

### Scope

* 涉及哪些模块。
* 哪些内容没有修改。

### Verification

* 执行了哪些命令。
* 哪些检查通过。
* 哪些检查失败或未执行。

### Database

* 是否修改 Schema。
* 是否包含 migration。
* 是否影响旧数据。

### Security

* 是否影响认证、权限和隐私。
* 是否存在新的风险。

### Deployment

* 是否修改部署配置。
* 是否新增环境变量。
* 是否需要额外部署步骤。

### Rollback

* 出现问题时如何安全回退。

涉及 UI 时，应附上必要的页面证据或截图。

## 18. 合并流程

合并前必须确认：

* PR 范围清晰。
* Review 已完成。
* CI 全部通过。
* 冲突已解决。
* migration 已检查。
* 文档已同步。
* 高风险修改已确认。
* 回滚方式明确。

不得为了快速合并而：

* 跳过失败检查。
* 删除测试。
* 关闭安全校验。
* 忽略 Review 意见。
* 强制覆盖目标分支。

## 19. 部署流程

部署前确认：

* 部署目标环境。
* 使用的 Commit。
* CI 状态。
* 环境变量。
* 数据库 migration。
* 对象存储配置。
* 回滚方式。
* 是否需要维护窗口。

部署后检查：

* 服务是否可访问。
* 核心页面是否正常。
* 核心接口是否正常。
* 登录和权限是否正常。
* 数据库读写是否正常。
* 文件上传和读取是否正常。
* 日志是否出现新增错误。
* 监控是否正常。

未实际部署时，不得声称功能已经上线。

## 20. 异常处理流程

发现严重问题时：

1. 停止继续扩大修改。
2. 保留日志和错误信息。
3. 记录触发步骤。
4. 判断影响范围。
5. 判断是否影响数据。
6. 判断回滚或前向修复。
7. 不执行未经确认的数据清理。
8. 修复后重新执行完整验证。

涉及生产数据时，优先保护数据完整性，不进行试探性破坏操作。

## 21. 最终交付

最终报告应包含：

* 任务结果。
* 核心修改。
* 修改原因。
* 涉及文件或模块。
* 数据库变化。
* 配置变化。
* 部署变化。
* 执行的验证。
* 通过的检查。
* 失败或未执行的检查。
* 剩余风险。
* 后续建议。

一项任务只有在实现、测试、文档和风险说明形成闭环后，才视为完成。
