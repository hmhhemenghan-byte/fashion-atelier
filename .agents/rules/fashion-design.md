# 工作空间 Rules

## 1. 项目定位

* 项目名称和品牌表达统一使用 `NÉRA ATELIER`。
* 本项目是面向独立时装设计师的作品、系列、样衣、发布、媒体、关系和生产准备工作台。
* 本项目不是电商平台。
* 未经明确产品决策，不得加入：

  * 商品价格
  * 购物车
  * 支付
  * 自动下单
  * 采购单
  * ERP 自动写入
  * 自动营销发送
* 系统不得自动发送邮件、即时消息、邀请或外联内容。
* 系统只能生成草稿、复制文案和人工登记已经发生的外部行为。
* 设计判断和关键批准必须由设计师人工完成，不得由系统自动决定。

## 2. 固定技术栈

项目固定使用：

* Node.js `>=22.13.0`
* npm
* TypeScript strict mode
* React 19
* Next.js 16
* Vinext
* Vite
* Cloudflare Workers
* Cloudflare D1
* Cloudflare R2
* Drizzle ORM
* Wrangler

不得擅自：

* 替换框架。
* 替换数据库。
* 替换对象存储。
* 切换包管理器。
* 引入与 Cloudflare Workers 不兼容的运行时能力。
* 将项目迁移到其他平台而不先设计适配层和迁移方案。

项目保持 ESM 模式。

## 3. 目录职责

* `app/`：页面、布局、Server Components 和路由。
* `app/api/`：HTTP Route Handlers。
* `lib/`：业务服务、权限、运行时适配、导出和共享逻辑。
* `db/schema.ts`：Drizzle Schema 唯一来源。
* `db/`：数据库连接和数据访问。
* `drizzle/`：数据库迁移文件。
* `worker/`：Cloudflare Worker 入口。
* `tests/`：测试和回归验证。
* `docs/`：业务阶段、数据口径、接口和迁移文档。
* `scripts/`：安装、构建和产物验证脚本。
* `.github/workflows/`：CI 和部署流程。
* `wrangler.jsonc`：Cloudflare Workers、D1、R2 和运行环境配置。

复杂业务逻辑不得直接复制到多个页面或 API 中。

共享查询、状态判断、权限检查和导出逻辑应进入 `lib/` 或专门的数据访问层。

## 4. Server 与 Client Components

* 默认使用 Server Components。
* 只有涉及以下浏览器能力时才使用 `"use client"`：

  * 本地交互状态
  * 浏览器事件
  * 文件选择
  * 拖放
  * 浏览器 API
  * 复杂即时交互
* Client Component 不得直接访问：

  * D1
  * R2
  * 管理员环境变量
  * 私密身份信息
  * 服务端权限逻辑
* 数据库、对象存储、身份验证和授权必须在服务端执行。
* 不得为了开发方便把整页或大范围组件树转换为 Client Component。
* 依赖当前登录身份的 Server 页面应避免错误静态缓存。

## 5. 身份认证与管理员权限

所有 Studio 管理写接口必须：

1. 拒绝非法跨域写入。
2. 验证 ChatGPT 登录身份。
3. 验证管理员邮箱权限。
4. 校验请求体。
5. 检查目标资源是否存在。
6. 检查当前业务状态是否允许操作。
7. 返回正确 HTTP 状态码。
8. 避免泄露内部异常信息。

优先复用现有能力：

* `getChatGPTUser()`
* `requireApiAdmin()`
* `rejectCrossOriginWrite()`
* `isAdminEmail()`

不得：

* 在客户端自行判断管理员身份。
* 仅通过隐藏按钮控制管理权限。
* 根据客户端传入的邮箱决定权限。
* 绕过统一权限函数直接实现临时管理员检查。
* 把真实管理员邮箱硬编码到业务源码。

`ADMIN_EMAILS` 必须通过运行环境配置。

## 6. 公共内容与私密数据边界

公共页面只能读取明确处于公开状态的数据，例如：

* 已发布作品。
* 已发布系列。
* 已发布过程记录。
* 已发布 Publication。
* 明确允许公开的媒体。

以下数据默认属于私密数据：

* 草稿。
* 内部备注。
* 联系人。
* 机会。
* 沟通记录。
* 外联对象。
* 样衣借调。
* 库存和盘点。
* 技术包。
* 试身记录。
* 试身图片。
* 封样证据。
* 生产放行。
* 生产偏差。
* 私享展厅内部信息。
* 邮箱和电话。
* 内部对象键。

公共查询不得通过“前端不显示”代替服务端过滤。

## 7. Private Showroom 规则

* 每个 Private Showroom 必须使用独立随机访问凭证。
* 数据库只保存凭证哈希和必要的末尾提示。
* 不得保存完整明文 Token。
* 原始 Token 不得进入：

  * 日志
  * 通用 API
  * Season Control Tower
  * Archive JSON
  * CSV 导出
  * 分析接口
* Token 轮换后，旧链接必须失效。
* 应支持明确到期时间和关闭访问。
* 展厅是否允许下载图片必须由显式配置控制。
* 受邀页面应避免被搜索引擎索引。
* 访问凭证只负责展厅访问，不得被扩展为 Studio 管理员权限。

## 8. D1 与 Drizzle 规则

* `db/schema.ts` 是数据库结构的唯一来源。
* Schema 修改后必须生成并提交 migration。
* 已经进入共享或生产环境的 migration 不得回写修改。
* 修正旧 migration 必须创建新的 migration。
* 不得通过删除表、清空数据或重建数据库规避迁移设计。
* 新字段必须明确考虑：

  * 数据类型
  * 是否允许为空
  * 默认值
  * 旧数据兼容
  * 唯一约束
  * 索引
  * 外键
  * 删除行为
  * 时间字段
* 多表写入必须考虑事务、失败回滚和部分成功。
* 状态字段必须使用受控值，不得在不同模块中使用不同拼写表达同一状态。
* ID、slug、业务编号和对象键必须保持稳定。
* 不得把仅供展示的名称作为永久业务主键。
* 删除父记录前必须检查级联影响。

## 9. 状态机规则

项目中的业务流程不得随意跳过阶段。

状态变更前必须检查当前状态是否允许目标操作。

典型业务流程包括：

* 草稿 → 发布
* 评审待定 → 修改后复审／通过／暂缓／退出
* 技术包草稿 → 评审 → 批准 → 锁定
* 试身草稿 → 评审 → 批准
* 封样创建 → 核对 → 批准 → `NERA-SEAL`
* 生产放行准备 → 批准 → `NERA-GO`
* 偏差报告 → 复核 → 决定 → 验证 → 关闭
* 外联对象提议 → 人工批准 → 草稿 → 人工登记发送／回复

不得：

* 直接修改数据库状态绕过业务验证。
* 允许客户端任意指定目标状态。
* 自动将未审核数据标记为批准。
* 将计划行为记为已经发生。

## 10. 人工决策边界

以下操作必须由设计师人工确认：

* 作品发布。
* 系列发布。
* Publication 发布。
* 设计评审结论。
* 材料批准。
* Look 用料批准。
* 技术包批准。
* 技术包锁定。
* 试身批准。
* 最终封样。
* 生产放行。
* 生产偏差决定。
* 联系人确认。
* 机会阶段推进。
* 外联对象批准。
* 外部已发送或已回复状态登记。

系统可以：

* 检查事实是否齐全。
* 提示阻塞条件。
* 计算准备度。
* 生成待办。
* 生成草稿。

系统不得：

* 自动批准。
* 自动发布。
* 自动锁定。
* 自动联系外部人员。
* 自动修改人工决策。
* 使用隐藏评分替代明确业务规则。

## 11. 不可变记录

以下记录一旦批准、冻结或完成，不得原地覆盖：

* Archive & Handoff 快照。
* 已批准的试身。
* 已批准或锁定的技术包修订。
* Final Sample Gate 封样。
* `NERA-SEAL`。
* Production Release。
* `NERA-GO`。
* 已形成的生产偏差决定。
* 已登记的历史互动。
* 审计记录。
* 已完成的批准事实。

后续修改必须创建：

* 新一轮。
* 新修订。
* 新时间线事件。
* 新快照。
* 新偏差记录。

不可变快照只允许新增和下载，不提供修改或删除接口。

## 12. R2 媒体规则

* R2 对象键必须稳定且不可预测。
* 不使用原始文件名直接作为唯一对象键。
* 上传时必须校验：

  * MIME 类型
  * 文件大小
  * 允许的文件类别
  * 空文件
  * 非法内容
* 不得只相信文件扩展名。
* 数据库写入失败时，应清理本次新增且未被引用的对象。
* R2 上传失败时，不得留下指向不存在对象的数据库记录。
* 替换媒体时不得破坏作品、系列或文档的稳定业务关系。
* 删除媒体前必须检查是否仍有其他记录引用。
* 公共媒体和私密媒体必须使用不同的访问和缓存策略。
* 私密媒体不得因为相关记录被批准而自动变成公共媒体。
* 新增媒体类型时必须同步 Archive Media Manifest。
* 所有公开图片必须维护有效且具体的 `altText`。

## 13. API 规则

所有 API 输入必须进行运行时校验和标准化。

推荐状态码：

* `400`：输入非法。
* `401`：未登录。
* `403`：无权限或来源非法。
* `404`：资源不存在。
* `409`：业务状态或并发冲突。
* `413`：文件过大。
* `429`：请求频率过高。
* `500`：服务端未预期错误。

API 不得返回：

* SQL。
* 数据库连接信息。
* 内部文件路径。
* 完整错误栈。
* 私密对象键。
* 展厅完整 Token。
* 不必要的个人信息。

状态变更接口必须：

* 校验当前状态。
* 校验目标状态。
* 校验必要前置条件。
* 防止重复提交。
* 处理并发冲突。
* 返回最小必要数据。

## 14. 导出规则

项目支持 JSON、CSV、iCal 等数据导出。

导出功能必须：

* 使用 UTF-8。
* 保持字段含义稳定。
* 防止 CSV 公式注入。
* 过滤敏感字段。
* 明确日期格式。
* 保留稳定 ID 和关联关系。
* 区分公开数据和内部数据。
* 对人工填报和已核验数据进行明确标识。

Archive & Handoff 修改时必须同步考虑：

* 新增数据表。
* 新增关联关系。
* 新增媒体类型。
* 新增对象键。
* 快照摘要。
* 版本号。
* 迁移兼容性。

不得静默遗漏新增业务数据。

## 15. 统计与指标规则

* 所有统计必须来源于可追溯事实。
* 预约、草稿、计划和提议不得计入已经发生的业务结果。
* 人工填报和已核验指标必须明确区分。
* 已核验数据必须保留来源。
* 不得虚构或推断不存在的第三方指标。
* 不得冒充 Launchmetrics MIV 或其他专有指标。
* 不同货币不得未经明确汇率、日期和换算规则直接汇总。
* 统计口径必须可解释，不使用隐藏权重。
* 新增指标时必须同步更新对应 `docs/phase-*.md`。
* 统计页面不得反向自动修改原始业务数据。

## 16. Season Control Tower 规则

* Season Control Tower 只汇总事实、阻塞和待办。
* 不自动改变任何业务状态。
* 不自动发布内容。
* 不自动批准记录。
* 不自动发送外联。
* 不返回展厅 Token、私人邮箱或电话等敏感信息。
* 准备度必须基于明确、可解释的检查项。
* 新增关键业务阶段时，应评估是否需要接入 Control Tower。
* 接入时必须避免重复计算和状态口径冲突。

## 17. UI 与视觉规则

* 保持高端、克制、编辑式的时装品牌视觉。
* 不使用与当前设计语言冲突的通用 SaaS 后台模板风格。
* 延续现有：

  * 字体层级
  * 间距
  * 留白
  * 排版节奏
  * 黑白和中性色体系
  * 编辑式命名
* 页面必须适配桌面端和移动端。
* 重要操作必须具备：

  * 加载状态
  * 空状态
  * 错误状态
  * 成功反馈
  * 禁用状态
* 状态表达不能只依赖颜色。
* 操作按钮文案必须明确说明实际行为。
* 危险操作需要清晰警示和二次确认。
* 不擅自进行全站视觉重构。
* 不使用无意义装饰破坏作品图片的主导地位。

## 18. 可访问性规则

* 所有公开图片必须提供准确替代文本。
* 装饰图片应正确标记为装饰用途。
* 表单控件必须具有关联标签。
* 错误信息必须能被理解和定位。
* 键盘用户应能完成主要操作。
* 焦点状态必须可见。
* 弹窗和侧栏必须处理焦点进入和返回。
* 不能只依赖颜色表示成功、错误或警告。
* 文字和背景需保持合理对比度。
* Digital Lookbook 应继续支持方向键、滚轮和触控操作。

## 19. 打印页面规则

以下页面修改后必须检查打印或保存 PDF 效果：

* Press Room。
* Line Sheet。
* Seasonal Coverage Book。
* 技术包。
* 生产资料。
* 其他 A4 交付页面。

打印页面应：

* 避免交互控件进入打印内容。
* 避免内容被分页截断。
* 保持图片比例。
* 保持标题和内容层级。
* 隐藏不必要导航。
* 确保黑白打印仍可理解。

## 20. 文档规则

以下变化必须同步更新 README 或 `docs/`：

* 架构。
* 运行环境。
* 页面和工作台。
* API。
* 数据表。
* Migration。
* 导出格式。
* Archive 版本。
* 统计口径。
* 权限和隐私边界。
* D1/R2 binding。
* 构建方式。
* 部署方式。
* 环境变量。
* 生产操作流程。

文档必须与仓库实际实现一致。

仓库已经实际使用 `wrangler.jsonc` 和 GitHub Actions Cloudflare 部署，不得保留与此冲突的旧说明。

## 21. CI 与部署规则

* `main` 为生产默认分支。
* 所有生产修改通过 Pull Request 合并。
* Pull Request 只执行验证，不部署生产。
* 只有合并或推送到 `main` 后才允许自动部署。
* 不在普通功能开发过程中手动部署生产。
* CI 应至少覆盖：

  * 依赖安装
  * lint
  * TypeScript 类型检查
  * 构建
  * Worker 产物验证
  * 集成测试
* 修改以下内容时必须单独说明部署影响：

  * `wrangler.jsonc`
  * `worker/`
  * `vite.config.ts`
  * `.github/workflows/`
  * D1 binding
  * R2 binding
  * 环境变量
  * migration
* Cloudflare API Token、Account ID 和其他密钥只能存放在 GitHub Secrets 或平台密钥管理中。
* 不得把生产凭证提交到仓库。

## 22. Git 与 Pull Request 规则

* 不直接在 `main` 开发。
* 分支名称使用：

  * `feat/<name>`
  * `fix/<name>`
  * `refactor/<name>`
  * `docs/<name>`
  * `test/<name>`
  * `chore/<name>`
* Commit 使用 Conventional Commits。
* 默认使用 squash merge。
* PR 必须说明：

  * 修改摘要
  * 影响范围
  * 数据库变化
  * 权限和隐私影响
  * 执行的验证
  * 部署影响
  * 回滚方案
* 涉及 UI 时，应提供必要的桌面端和移动端证据。
* CI 未全部通过时不得合并。

## 23. 测试规则

修改业务功能时必须覆盖对应路径。

API 测试应考虑：

* 正常请求。
* 非法输入。
* 未登录。
* 无权限。
* 跨域写入。
* 资源不存在。
* 当前状态不允许操作。
* 重复提交。
* 并发冲突。
* 文件过大。
* 对象存储失败。

数据库修改应测试：

* 新建数据库。
* 已有数据库升级。
* 默认值。
* 外键。
* 唯一约束。
* 级联删除。
* 查询索引。
* 导出。
* Archive。

UI 修改应测试：

* 正常数据。
* 空数据。
* 长文本。
* 缺失媒体。
* 加载失败。
* 移动端。
* 键盘操作。
* 打印布局。

## 24. 禁止事项

不得：

* 绕过权限层直接访问管理写接口。
* 将管理员邮箱硬编码到源码。
* 保存 Private Showroom 明文 Token。
* 公开试身和封样私密图片。
* 修改已冻结历史记录。
* 自动批准设计决策。
* 自动发送外联消息。
* 伪造第三方影响指标。
* 把计划行为统计为已发生事实。
* 回写已经应用的 migration。
* 直接修改生产 D1 代替 migration。
* 删除生产 R2 对象而不检查引用。
* 为通过 CI 删除测试或降低安全校验。
* 提交 `.env`、Token、密钥或生产凭证。
* 擅自把项目改造成电商或 ERP 系统。

## 25. 完成标准

任务只有同时满足以下条件才算完成：

* 符合明确验收标准。
* 修改范围与任务一致。
* 没有无关重构。
