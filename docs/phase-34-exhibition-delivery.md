# Phase 34 — Exhibition Delivery Desk / 展览交付台

## 目标

把已经批准并冻结的展览释读修订转化为可逐项校样、可人工放行的交付主档。入口导语、叙事章节、作品标签、策展署名、无障碍说明和权利说明都保留对冻结来源的直接引用。

本阶段不自动排版、翻译、印刷、上传、公开或发送，也不把“交付定义已批准”伪装成“外部已经收到”。

## 数据结构

### `exhibition_delivery_packages`

每个交付包绑定一个已批准或已关闭的释读修订，并按修订号保存交付负责人、对象或场景、计划时间、主档标题、格式标准、位置与层级标准、无障碍标准、权利标准、交接说明和人工批准依据。

状态按 `draft / in_review / approved / closed / void` 推进；人工决定为 `pending / release / revise / hold`。批准后不可改写，新的交付定义必须建立下一修订。

### `exhibition_delivery_items`

建立交付包时，系统按冻结释读自动生成完整来源清单：

- 主语言入口导语；
- 每个章节的已启用语言版本；
- 每件作品标签的已启用语言版本；
- 策展署名、无障碍说明与权利说明。

每项独立保存交付载体、顺序、标题、位置、版式要求、`draft / ready / hold / omitted` 校样状态、校样依据与交接备注。来源正文不复制进交付表，始终从冻结释读事实读取。

## 人工批准

批准前必须满足：

- 交付负责人、对象、计划时间、主档标题和五类交付标准齐全；
- 冻结释读中的每个必要来源都有对应交付项；
- 全部必要来源均明确为 `ready`；
- 每个就绪项都有载体、位置、版式要求、校样依据和交接备注；
- 来源文字仍然存在且与冻结释读可追溯；
- 设计师明确选择 `release`。

系统只验证事实覆盖与交付准备，不评价版式美学、翻译质量或外部制作结果。

## 接口与导出

```text
GET   /api/studio/exhibition-delivery
POST  /api/studio/exhibition-delivery
PATCH /api/studio/exhibition-delivery/:id
PATCH /api/studio/exhibition-delivery/items/:id
```

全部接口要求设计师管理员身份并拒绝跨源写入。支持交付包 CSV、交付项 CSV 与完整 JSON 导出。

## 控制塔与归档

- Season Control Tower 新增第 24 道“展览交付签核”事实关卡；
- 等待校样、补齐或要求修改的交付包进入行动议程；
- Studio Map 扩展为 33 个业务工作台；
- 完整交接格式升级为 `nera-archive/25`；
- 新增 D1 迁移由 Drizzle 生成并随本阶段提交。

## 边界

- 不自动生成或改写冻结释读文字；
- 不自动排版、翻译、印刷、上传、公开或发送；
- 不记录虚构的“已外部交付”状态；
- 不扩展为场馆、票务、预算、采购、保险或合同系统；
- 所有交付判断与放行均由设计师明确完成。
